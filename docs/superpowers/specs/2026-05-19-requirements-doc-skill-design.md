# 要件定義スキル (`requirements-doc`) 設計仕様

| 項目 | 内容 |
|---|---|
| 作成日 | 2026-05-19 |
| ステータス | Draft |
| 対象スキル名 | `requirements-doc` |
| 保存先 | `config/claude/skills/requirements-doc/SKILL.md` → `~/.claude/skills/requirements-doc` (symlink) |

## 1. 背景

新サービス立ち上げ時に、チーム内共有用の要件定義書をブレなく書き起こせるスキルが欲しい。既存スキル調査の結果、近いものはあったが過不足あり:

- `superpowers:brainstorming` — 出力が技術設計寄りで PRD 形式の章（ペルソナ / ユーザーストーリー / KPI / Non-Goals）を持たない
- `daishiman/AIWorkflowOrchestrator` の 8 個の専門スキル群 — 完全分業でエンタープライズ重厚すぎる
- `wasabeef/claude-code-cookbook` の `plan` — 計画一般、要件定義特化ではない

そのため独立した軽量スキルを新規作成する。

## 2. スコープ

### 2.1 対象 (In-Scope)

- 1 セッション内に対話だけで要件定義書 1 本を完成できる
- チーム内共有用に十分な構造（PRD + 機能要件 + 非機能要件 + 制約事項）を持つ
- 既存システム置換 / 拡張 / 新規 の 3 つのコンテキストに伸縮対応
- 業界標準テクニック（MoSCoW / Given-When-Then / ISO 25010 / 5W1H）を質問とテンプレに組み込む

### 2.2 対象外 (Out-of-Scope)

- 業務フロー As-Is / To-Be 図、画面定義、帳票定義（日本式重厚要件定義書の範囲はやらない）
- WBS / スケジュール / 工数見積（別スキル `pm-wbs` 相当の領域）
- 実装計画への自動遷移（`writing-plans` 連携はしない。要件定義で完結させる）

## 3. スキル基本仕様

| 項目 | 値 |
|---|---|
| 名前 | `requirements-doc` |
| 場所 | `config/claude/skills/requirements-doc/SKILL.md` |
| シンボリックリンク | `~/.claude/skills/requirements-doc/` (install.sh 経由) |
| `description` トリガー | 「要件定義」「要件まとめて」「新サービス作る」「requirements」「PRD 書きたい」「要件書きたい」 |
| 引数 | `--service <name>`（任意。指定無ければ対話で聞く） / `--path <dir>`（任意。デフォルトは `docs/requirements/`） |
| `allowed-tools` | `Bash(git add:*), Bash(git status:*), Bash(git commit:*), Bash(mkdir:*), Read, Write, Edit` |
| 言語ポリシー | SKILL.md 自体は英語（dotfiles ルール準拠）、対話プロンプトと出力テンプレは日本語 |
| 出力先（デフォルト） | `docs/requirements/YYYY-MM-DD-<service-slug>.md` |

### 3.2 主要データフロー

### 4.2 条件分岐ルール

セクション「3. 現状システム構成」は、対話冒頭の質問で **既存システム置換 / 拡張のとき** のみ含める。**完全新規 (greenfield)** の場合はテンプレから章ごと削除し、以降の番号を繰り上げる。

## 5. 対話フロー

```
1. 起動時:
   - サービス名確認（引数で来ていなければ聞く）
   - コンテキスト分岐質問（多肢選択）:
     [完全な新規 / 既存システムの置き換え / 既存システムの拡張・連携]
   - greenfield なら「3. 現状システム構成」章をテンプレから除去

2. セクション 1 (概要) から順に、セクションごとに「核心の 1 問」を聞く:
   - TL;DR は 5W1H（誰が・いつ・どこで・何を・なぜ・どのように）を満たすよう質問
   - 不明点があれば追加で 1-2 問掘り下げる（1 セクションあたり最大 3 問）
   - ユーザーが「あとで」「TBD」と答えたら `<!-- TBD: ... -->` で残して次へ

3. セクション完了ごとに、書いた内容を表示してユーザー確認

4. 機能要件セクションでは:
   - 機能を 1 つずつ追加（「次の機能を追加しますか？」で繰り返し）
   - 各機能に MoSCoW 優先度を 4 択で聞く
   - 関連する US がある場合は紐付け

5. ユーザーストーリーセクションでは:
   - 各 US に Given-When-Then の受け入れ基準を最低 1 つ書かせる（必須ではなく強推奨）

6. 非機能要件セクションでは:
   - ISO 25010 の 7 項目を 1 つずつ聞き、不要なら「N/A（理由：...）」を書かせる
   - 空欄禁止のルールで漏れチェックとして機能させる

7. 全セクション完了後:
   - ファイル全体をプレビュー表示
   - ユーザー確認 → 保存
   - `git add` してコミット提案
     - メッセージ: `docs(requirements): add <service-slug> requirements`

8. 保存後:
   - TBD が残っていれば一覧表示
   - 「埋めるための次のアクション」を提案
```

## 6. 既存ファイル衝突時の処理

同名ファイルが既にある場合は、**保存直前に上書き可否を確認するのみ**（YAGNI で初版は最小実装）。
- 上書き OK → そのまま保存
- 上書き NG → 別名（例: `<service-slug>-v2`）を提案して再確認

更新モード（既存ファイル読み込み → 未記入セクションのみ埋める）は、需要が出てきた段階で追加する。

## 7. 取り込んだ業界標準テクニック

| テクニック | 出典 | 適用箇所 |
|---|---|---|
| 5W1H | 一般的なインタビュー技法 | TL;DR 章の質問 |
| MoSCoW | DSDM / アジャイル | 機能要件の優先度欄 |
| Given-When-Then | BDD / Gherkin | ユーザーストーリーの受け入れ基準 |
| ISO/IEC 25010 | 国際規格 | 非機能要件の 7 大カテゴリ |
| Non-Goals 章 | Google / Amazon PRD 文化 | スコープ明確化 |

## 8. 実装ステップ

1. `config/claude/skills/requirements-doc/SKILL.md` を作成
2. `install.sh` は `config/claude/skills/*/` を自動シンボリックリンクするので追加修正不要。手動リンクの場合は `ln -s $PWD/config/claude/skills/requirements-doc ~/.claude/skills/requirements-doc`
3. `/reload-plugins` でスキルを反映
4. 試運転として 1 つの新規サービスで要件定義を起こしてみる
